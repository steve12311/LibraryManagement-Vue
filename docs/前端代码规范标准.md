# 前端代码规范标准

## 🎯 目标

本规范适用于当前图书管理后台前端项目，目标是统一以下事项：

- 代码风格一致
- 类型边界清晰
- 页面职责明确
- 变更可审查、可回归、可维护

本规范优先级：**可读性 > 正确性 > 可维护性 > 开发速度**。

---

## 1. 通用原则

### 1.1 基本要求

- 默认使用 `TypeScript` 与 Vue 3 `script setup`。
- 代码以“**清晰表达业务意图**”为第一目标。
- 新增代码必须处理异常分支和边界条件。
- 禁止保留无用代码、注释掉的大段旧逻辑、临时调试逻辑。

### 1.2 变更原则

- 一次提交只解决一类问题。
- 修改功能时优先修复根因，不做表面兼容补丁。
- 非任务范围内的问题可以记录，但不要顺手扩大改动面。

---

## 2. 目录职责规范

### 2.1 页面层

- `src/pages/`：放页面骨架或布局页，例如登录页、主页、个人中心页。
- `src/views/`：放业务视图页。
- 页面文件只负责：页面编排、页面状态协同、页面级事件入口。

### 2.2 组件层

- `src/components/`：放可复用组件。
- 通用组件不得直接依赖具体业务字段名，必须通过 `props`、`slots`、事件暴露能力。
- 业务弹窗、表单片段优先拆为组件，不允许长期堆在页面文件中。

### 2.3 数据层

- `src/api/`：只负责接口定义、请求参数映射、返回类型声明。
- `src/store/`：只负责跨页面共享状态与业务状态协调。
- `src/utils/`：只放纯工具或跨模块基础设施，不放页面私有逻辑。
- `src/composables/`：封装可复用状态逻辑、查询逻辑、弹窗逻辑、上传逻辑。

---

## 3. 命名与导入规范

### 3.1 命名规范

- Vue 组件文件：`PascalCase.vue`
- API 模块文件：`kebab-case`，例如 `user-api.ts`
- store 文件：`kebab-case`，例如 `user-store.ts`
- 组合式函数：`useXxx.ts`
- 类型名 / 接口名：`PascalCase`
- 变量 / 函数：`camelCase`
- 常量：语义明确，模块内常量用 `camelCase`，跨模块固定值可用 `UPPER_SNAKE_CASE`

### 3.2 导入规范

- 跨目录引用统一使用 `@/`。
- 同目录或极近目录允许使用相对路径。
- TypeScript 模块导入默认 **不写 `.ts` 后缀**。
- 导入顺序建议如下：
  1. 第三方库
  2. 类型导入
  3. `@/` 业务模块
  4. 相对路径模块

---

## 4. TypeScript 规范

### 4.1 `any` 使用规则

- 默认禁止显式 `any`。
- 优先使用 `unknown` + 类型收窄。
- 确实无法避免时，必须满足以下条件：
  - 仅出现在第三方库边界或临时迁移边界；
  - 附带中文说明；
  - 后续可继续收敛。

### 4.2 Promise 与异步规范

- 已有 Promise 的异步调用，禁止再手动包 `new Promise`。
- 统一优先使用 `async/await`。
- catch 中必须说明错误处理策略：继续抛出、用户提示、降级处理三者至少明确一种。

### 4.3 类型建模规范

- 接口返回统一显式声明类型。
- `ApiResponse<T>` 默认泛型应为 `unknown`，而不是 `any`。
- 表格行、表单模型、查询参数、上传结果都必须有独立类型。
- 避免 `as any`、`as unknown as Xxx` 连续断言。

---

## 5. Vue 组件规范

### 5.1 单文件组件结构

推荐顺序：

1. `import`
2. 类型声明
3. `props` / `emits` / `model`
4. 状态定义
5. `computed`
6. `watch` / 生命周期
7. 事件处理函数
8. 与接口交互函数

### 5.2 页面与组件体量限制

- 普通组件建议不超过 **200 行**。
- 业务页面建议不超过 **300 行**。
- 超过 **500 行** 视为必须拆分。

### 5.3 模板表达式规范

- 模板中禁止出现复杂链式表达式。
- `filter` / `map` / `reduce` / 多层可选链调用应移到 `computed` 或函数中。
- 复杂 `:ui` 配置对象、表格列定义、下拉菜单项应抽为常量或计算属性。

### 5.4 组件边界规范

- 通用组件只暴露最小必要能力。
- 组件输入必须可预测，不允许隐式依赖外部全局状态。
- 子组件对父组件只通过 `props` / `emit` / `slot` 通信。

---

## 6. API 与状态管理规范

### 6.1 API 模块规范

- 每个 API 方法必须声明：请求参数类型、返回值类型、接口路径语义。
- API 层不处理页面 UI 细节，不直接弹 toast。
- 上传、下载、导出等特殊请求要单独封装，不混入普通列表接口。

### 6.2 Store 规范

- store 只保留跨页面共享状态和业务流程协调。
- store action 应直接返回结果，不额外包 Promise。
- store 中不得堆积页面专属弹窗状态。
- 重置逻辑必须完整、可复用、可测试。

### 6.3 请求层规范

- 请求拦截器负责公共 header、token、响应解包。
- 业务错误码处理集中在请求层或专门错误处理中间层。
- 请求层中使用的第三方对象必须有明确类型，不允许 `httpRequest: any`。

---

## 7. 错误处理与日志规范

### 7.1 用户提示

- 面向用户的错误必须给出可理解提示。
- 提示文案使用中文，避免直接暴露英文异常原文。
- 同一错误避免多次重复弹出。

### 7.2 开发日志

- 禁止将调试用 `console.log` 提交到主分支代码。
- `console.error` 仅允许用于无法继续执行的异常场景。
- 推荐引入统一 `logger`，按环境控制输出级别。

---

## 8. 样式与 UI 规范

### 8.1 样式书写

- 优先使用现有 UI 体系与 Tailwind 工具类。
- 同类组件保持统一视觉风格，不随页面自由发挥。
- 局部样式优先写在组件内；可复用样式再抽全局。

### 8.2 可维护性要求

- 重复出现的样式片段应抽成类名、配置对象或组件。
- 大型 `:ui` 配置对象应提取为常量。
- 非当前页面必须加载的样式，禁止全局引入。

---

## 9. 性能规范

### 9.1 加载策略

- 非首屏功能必须优先考虑异步加载。
- 大型依赖不得默认进入首屏主包。
- 新增第三方依赖前，需要评估体积与替代方案。

### 9.2 列表与图片

- 列表页必须具备分页、加载态、空态、异常态。
- 图片地址解析、格式化等逻辑允许做本地缓存，但必须避免内存无限增长。
- 大列表或复杂卡片渲染应关注重复计算与不必要 watch。

### 9.3 日期与工具库

- 新增日期处理优先使用原生 `Intl` / `Date` 或更轻量方案。
- 原则上不再新增 `moment` 依赖使用面。

---

## 10. 仓库卫生规范

- 禁止提交 `.DS_Store`、临时文件、IDE 本地缓存、构建中间产物。
- 生成文件和源码文件必须分离。
- 修改依赖时同步检查 lockfile 和构建结果是否合理。

---

## 11. 提交前检查清单

每次提交前至少完成以下检查：

1. 代码可读，命名清晰，无无用注释。
2. 无新增 `any`、无新增调试日志。
3. 关键异常路径已处理。
4. 类型检查通过：`pnpm exec vue-tsc -b --pretty false`
5. 构建通过：`pnpm build`
6. 涉及 UI 的变更已手工验证关键流程。

---

## 12. Code Review 检查清单

review 时重点检查以下内容：

- 是否引入了新的 `any` 或弱类型断言。
- 是否把业务逻辑堆进了模板表达式。
- 是否在页面文件中塞入过多弹窗、表单、上传逻辑。
- 是否存在重复请求、重复 toast、重复状态。
- 是否新增了无法按需加载的大型依赖。
- 是否修改了公共请求层、鉴权层但没有回归关键链路。

---

## ✨ 落地要求

本规范从当前版本开始执行，后续新增或重构代码必须遵守；历史代码不要求一次性全部推倒，但 **改到哪里，就把哪里收敛到规范内**。

---

## 13. Serena 复审补充规范

### 13.1 增量零告警原则

- 对于当前任务触达的文件，提交前必须清零 ESLint warning。
- 历史遗留 warning 可以分批治理，但不得在已修改文件中“原样带过”。
- 若确有暂时无法清零的第三方边界，必须在代码附近补充中文说明，并登记到整改清单。

### 13.2 请求泛型规范

- `request<Req, Res>` 的 `Req` 禁止使用 `any`。
- 无请求体的接口统一使用 `request<unknown, Res>`，不要再写 `request<any, Res>`。
- `params`、`data`、路径参数的来源类型必须清晰，禁止用 `as any` 强行打通。
- API 层方法必须能从签名直接看出“请求入参”和“响应结果”的边界。

### 13.3 事件通信规范

- 默认优先使用 `props` / `emit` / `composables` / `Pinia` 传递状态与事件。
- 若确实需要全局事件总线，必须满足以下要求：
  - 事件名和参数基于 `EventMap` 泛型约束；
  - `on` 必须返回取消订阅函数；
  - 缓存事件必须具备清理策略、容量上限或失效机制；
  - 禁止使用 `string + any[]` 作为长期事件协议。

### 13.4 页面适配与缓存规范

- DTO 到表单模型的转换、提交前归一化、树节点缓存、选项缓存，不得长期堆在页面 SFC 中。
- 这类逻辑应优先抽到 `src/composables/` 或同目录 `model.ts` / `adapter.ts` 文件。
- 页面层只保留三类职责：页面编排、页面级状态协同、事件入口。
- 当单页同时包含“列表 + 弹窗 + DTO 适配 + 本地缓存”时，默认视为需要拆分。

### 13.5 错误处理契约

- `catch` 中禁止只保留 `console.log` 或 `console.error`。
- 每个异常分支至少明确一种处理动作：用户提示、状态回滚、继续抛出、返回受控结果。
- 同一页面内同类操作（查询、提交、删除、状态切换）的错误提示文案应保持一致。
- 生产代码中禁止提交纯调试日志；调试期日志必须在合并前删除。

### 13.6 类型导入规范

- 仅用于类型的位置必须使用 `import type`。
- 全局声明文件优先使用顶层类型导入，不再混用 `import()` 内联类型写法。
- 需要跨模块复用的类型，应放到明确的类型文件中，而不是散落在业务页面内部声明。
